For each, the owner chooses one of: Options: approve a supported-subset contract (written next to the code, marked not an upstream guarantee, rechecked at each update) | ask upstream (an outward action, the owner's go) | stop relying on it.

- Point 2, zig/src/serve.zig:1329-1350: accept and pool callbacks run on their own loop's thread because the loops share no zio LoopGroup (zio src/ev/loop.zig:559-563, src/ev/sockreg.zig:105, 213-315). zio documents only "Called on the loop's thread" (src/ev/completion.zig:294). Guards exist (serve_test.zig checks, `pg.ownLoop` panic). Asking upstream would be a question on https://github.com/lalinsky/zio issues: "is an ungrouped loop guaranteed to complete only its own socket ops, on its own thread?"
- Point 3, zig/src/pg.zig:60-71: the pool polls a dup of libpq's socket because a zio socket registration lives until `NetClose` and closing a descriptor with a parked op is asserted against (src/ev/sockreg.zig:20-22, 357-375; kqueue.zig:634-641; epoll.zig:609-616). Stopping would mean registering libpq's own descriptor, which libpq closes and replaces (PQfinish, PQconnectPoll) — not available without the registration contract; the realistic options are a supported-subset contract or asking upstream.
- Point 5, test/retained.c:13-25: (a) `calloc` and `realloc` are hand-declared; C11 7.1.4p2 does not cover them (they use `size_t`), so they rest on the toolchain's libc, as lean.h's own `malloc`/`free` declarations do (lean.h:524, 582). (b) `mi_usable_size` of a Lean object pointer gives its block only because the runtime returns mimalloc's pointer (lean.h:527-548, lean4 src/runtime/mimalloc.cpp:39-52, src/runtime/object.cpp:365-378). Note: lean.h already declares `mi_usable_size` through lean/mimalloc.h when lean/config.h defines LEAN_MIMALLOC (it does in this toolchain), so the hand declaration is redundant; "stop relying" for (b) could mean using lean.h's declaration under `#ifndef LEAN_MIMALLOC #error`, which still leaves the layout assumption.
- Point 6, lakefile.lean:19-71 (`glibcVersion`, `zsrvTarget`): the toolchain ships glibc as `lib/glibc/libc.so` without its version (lean4 script/prepare-llvm-linux.sh:59-64), so the version is read from the library's version names. The Reference Manual documents only the supported floor ("x86-64 Linux with glibc 2.26+", "aarch64 Linux with glibc 2.27+", Manual/SupportedPlatforms.lean:28-29), which is not a statement of the glibc the toolchain links against.
