Find why lean-db reaches only 0.64 of Go at one connection in the Linux container

Seen in rqc3ql's container run of ./bench.sh (2026-11-18, OrbStack arm64, epoll, one run): lean-db c=1 10,266 req/s, p50 90 µs, 34 µs CPU per request; go-db c=1 15,889 req/s, p50 45 µs, 29 µs CPU; at c=64 lean-db is 1.61 of Go. On macOS the same commit gave 1.12 and 1.25. Plain HTTP at c=1 is at parity in the container (lean-h1 20.5 µs p50, go 20.3 µs). Go got 59 % faster moving to Linux (macOS 9,945 req/s, 83 µs CPU) while lean-db stayed level, so the gap is the DB round trip at one connection: about 70 µs of DB overhead in lean-db's p50 against 25 µs in Go's, with CPU per request close.

Consult round 20261118-155040-3924 at the owner's request (sol ea5f6ca3, argon 98cf841d): both call it worth investigating and say one run under the shared host's load does not establish it. Argon's guess that lean-db does not try a receive before parking is refuted by zig/src/pg.zig:166-169 (zio tries the receive first); its other candidates (epoll registration churn per one-shot peek re-arm, an extra loop turn between PQflush and the receive, libpq's second recv) are open.

Proposed plan (measurement only, no change): in the container, c=1 only, paired rounds alternating lean-db-first and go-db-first, each ending at the same completed-request count; report per-pair ratios, p50 and CPU per request, and voluntary context switches per request from /proc. If the gap holds, count syscalls per request for both servers (strace -c or perf trace over a fixed number of requests) and, on lean-db, timestamp send/flush, peek completion and result delivery to split loop wake-up from libpq work. Record the result in README "lsrv-db" with the container's numbers, and propose a fix as its own item only from what the measurement shows.
