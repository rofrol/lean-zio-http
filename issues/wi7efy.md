Make serve.zig correct and efficient under io_uring

Requested by the user on 2026-11-17: do the work of making serve.zig correct under io_uring (option (2) of mzqamr, which had chosen to pin epoll and leave io_uring unsupported; this request supersedes that "unsupported" verdict as the end state).

Background (mzqamr, ogcdwm's diagnostic run in the OrbStack arm64 container, kernel 7.2.12, zio 830564437b2c): io_uring queues an SQE at `loop.add` and never tries the syscall first (zio src/ev/backends/linux/io_uring.zig `submitInner`), while the readiness backends do (src/ev/sockreg.zig `submitIo`). So serve.zig's `sendParked` (phase `.running` after `loop.add`) is true for every send: the readiness poll starts beside every send (test "a response sent at once starts no poll" fails, `conn.polls` 1), and the tests relying on inline completion fail (7 of 22 at the time; see mzqamr's and emb2ob's commits for the current tests). A positive kernel event for "this send waits in the kernel" exists under io_uring: `/proc/self/fdinfo/<ring fd>` lists `PollList:` / `op=26` with no CQE (a debugging interface, not an ABI).

Work:
- Design first, with a consult round: what "the send is parked" means on a completion backend (for example, the send's completion has not arrived by the end of the loop's current tick, or an explicit zio signal, if zio offers one), so the readiness poll beside a send still starts only when the send really waits, on every backend. Check zio's docs and source at the pin for what it guarantees (policy Rule 6: no reliance on undocumented zio behavior without recording it; a zio bug goes the fork path, not a local workaround).
- Implement it so serve.zig behaves the same on kqueue, epoll and io_uring, with Lean's state machine unchanged where possible.
- Tests: the transport suite passes under epoll and io_uring in the Linux container (ogcdwm's setup) and on macOS. Restate each backend-dependent test so it waits for a positive event on each backend (for io_uring, the fdinfo event or a better one from the design), never a timing.
- The build: keep the epoll pin until io_uring passes. Then allow both backends and say which one the deployed server uses; the choice between them comes from 53rwgc's VPS numbers, and a change of the deployed backend is told to ekklesiai.org by the coordinating session.
- Measure the per-request cost under both backends in the container (bench, CPU per request) and report it.
