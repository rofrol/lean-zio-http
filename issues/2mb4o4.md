Decide whether to propose cheaper head parsing to leanprover/lean4's Std.Http, or accept H1's parse cost

Found by item owgate (docs/reports/h1-parse-profile.md, "What follows").

H1's parse is about 2.7 µs per pipelined request and 4.0 µs per baseline-get one on the M1 (130 and 189 small allocations), and about nine tenths of it is `Std.Http`'s own work; the adapter's code and its per-request buffer copy are about 3 %, so nothing in this repository pays. The largest parts, in the same shares on the M1 and in the Linux container: the request line 29 % (39 % baseline-get), field-line syntax 19 %, the Host value parsed again as a URI host by `hasSingleAcceptedHostHeader` 13 % (20 % for `localhost:8080`), field names and values re-checked as strings 11 %; across them, the allocator and reference counting about 35-40 % of self samples, and `Std.Internal.Parsec.ByteArray.scanWhileUpTo` calling its predicate as a closure per byte (7.7 % self plus most of `lean_apply_1`'s 5.5 %).

These are not bugs under AGENTS.md, Rule 6 (no performance contract found in Std.Http's documentation), so no fork applies; a change is an upstream performance contribution, an outward action that needs the owner's go.

Options:
1. Draft (in docs/upstream/) and, with the owner's go, open an issue at leanprover/lean4 with the profile and `lsrv-parsebench` as reproducer, suggesting: `@[specialize]` on `scanWhileUpTo` (or inlining it into its callers), validating the Host value without a second URI parse, not re-checking field values `parseFieldLine` already scanned, and fewer `ByteSlice.toByteArray` copies; then a PR for whichever upstream welcomes.
2. Accept the cost and record it as decided (a DECISIONS.md entry).
3. Defer until a load run shows the parse limits a requirement this project has.
