How a PostgreSQL result over Query.maxResultBytes is received and how it ends the session

Needs a decision (proposed by tc5rsx, investigation only; it belongs under "Needs a decision").

## What is at issue

`ekk_pg_collect` (zig/src/pg.c) takes each statement result whole from libpq (PQgetResult) and only then `rows_of` checks it against `Query.maxResultBytes` (1 MiB) and answers `54000`. So an oversized result costs its full size (libpq's PGresult) per pool slot before it is rejected. Item tc5rsx compared libpq's row-by-row modes to stop at the bound instead.

## Findings (libpq source REL_14_STABLE to REL_18_STABLE of the github.com/postgres/postgres mirror, read 2026-11-17)

1. Modes and versions. The pool needs libpq >= 14 (pipeline mode; the repository documents no minimum; the local libpq is 18.6). Single-row mode (`PQsetSingleRowMode`) exists in 14+ and is documented for pipeline mode since 14 (libpq.sgml, pipeline "Processing Results": "call PQsetSingleRowMode before retrieving results with PQgetResult. This mode selection is effective only for the query currently being processed"). Chunked mode (`PQsetChunkedRowsMode`, `PGRES_TUPLES_CHUNK`) exists only in 17+ (absent from libpq-fe.h of 14 to 16): using it makes libpq 17 the build and runtime minimum (a link-time symbol). In 17+ single-row mode is chunked mode with a chunk of 1 (`partialResMode`, `maxChunkSize = 1` in fe-exec.c).
2. When the mode can be set. Both setters succeed only while `asyncStatus == PGASYNC_BUSY`, the head of libpq's command queue is a simple or extended query, and no result for it has been started (`canChangeResultMode` in 17, the same tests inline in 14). On a statement's first use the pool sends Prepare + Execute + Sync, so right after sending the queue head is the Prepare and the setter fails; the mode must be set after PQgetResult returned the Prepare's terminating NULL (then `pqPipelineProcessQueue` makes the Execute the head) and before the next PQisBusy/PQgetResult parses the Execute's RowDescription. For a cached or unnamed execution it can be set right after sending. No public setter targets a later queue entry. The collector needs an explicit "between commands" state for this: `p->preparing` is cleared on the Prepare's result, before that boundary.
3. A fix the pool would depend on: "libpq: Reset singlerow flag correctly in pipeline mode" (b8af4166ff on REL_14_STABLE, 27ca0bce5f on REL_15_STABLE, db1b931a4e on master) is in 14.6, 15.1 and 16.0 and later, not in 14.0 to 14.5 or 15.0. The pool's Sync always follows the Execute in the queue, which the bug's description (the query last in the queue) suggests is unaffected, but that is untested; the minimum would be stated as 14.6 on 14.x, 15.1 on 15.x, any 16+.
4. No libpq mode bounds a single row. libpq parses a protocol message only once it is whole in `conn->inBuffer` (fe-protocol3.c, pqParseInput3: "Can't process if message body isn't all here yet", enlarging the buffer with pqCheckInBufferSpace); DataRow is a `VALID_LONG_MESSAGE_TYPE`, so it has no size sanity limit. One row therefore costs its full size in the input buffer, and again in its PGresult (pqRowProcessor copies the values), before the pool sees any of it. The pool sets no bound on a row's size (the text form of a value can be larger than its stored form, e.g. bytea's hex output).
5. libpq's input buffer only grows. It starts at 16 KiB per connection (fe-connect.c) and pqCheckInBufferSpace (fe-misc.c) only enlarges it; nothing shrinks it before PQfinish. A session that once received a large row keeps that capacity for its life; closing the session is what reclaims it.
6. In a row mode the parser stops after each ready row or chunk until PQgetResult takes it, and pqReadData reads only into existing free space (adding 8 KiB of headroom when less is free). Since the pool takes every ready result after each PQconsumeInput, the input buffer's capacity is expected to stay near the larger of 16 KiB and the largest message, with geometric slack. This is an expectation from the code, not a guaranteed bound.
7. Row modes return `PGRES_SINGLE_TUPLE` (or `PGRES_TUPLES_CHUNK`) results, then a zero-row `PGRES_TUPLES_OK`; an error after some rows arrives as `PGRES_FATAL_ERROR` after them. Today's switch in `ekk_pg_collect` would send the partial statuses to its error branch, and its last-result-wins rule would let the final zero-row result replace the rows: an implementation must accumulate rows and keep the columns for a zero-row result.
8. What 54000 means today: it is answered after the Sync, so a statement that succeeded has run and its implicit transaction committed (a write with a large RETURNING is applied and answered 54000). Closing the session when the bound is crossed mid-result makes the outcome unknown: the server may already have committed, or may roll back when it notices the closed connection, which it does eventually, not necessarily at its next send. Closing undoes no non-transactional effects (sequences).
9. A separate gap the bound has today (its own proposed item, "Count each row and field in Query.maxResultBytes"): `rows_of` counts only text bytes, so many NULL or empty values pass the bound at almost no counted cost.

## Options

A. Single-row mode, dispose of the session on overflow (recommended). Set single-row mode for every execution (after the Prepare's NULL on first use), checking the setter's result: a failure is a programming error, never a silent fallback to whole-result mode. Convert each row to Lean values as it arrives, charging it against the bound before allocating; when the charge crosses the bound, drop the accumulated rows, answer 54000 once with a message saying the statement's outcome is unknown, and close the session through the existing close-after-answer path (`ekk_pg_collect` returning -1, as for COPY and a transaction left open). Contract changes: `Query.Result.error`'s doc (Server/Query.lean) and README "Results and errors" say that 54000 for an oversized result leaves the statement's outcome unknown, like 08006, and is not to be retried on its own; the memory statement becomes: the pool bounds the result data it accumulates; libpq may still hold memory proportional to one whole protocol message, a single oversized row included, until overflow closes the session. Works on libpq 14.6/15.1/16+. Cost: one PGresult per row (to be measured with the existing load runs before adoption).
B. Chunked-rows mode, dispose on overflow: as A with `PQsetChunkedRowsMode` (fewer PGresult allocations), but libpq 17 becomes the minimum for building and running the server, for ekklesiai.org too. Keeping both modes behind a version check is compatibility machinery and is not proposed.
C. A row mode, but on overflow discard the rest of the result through the Sync and keep the session: the accumulated memory stays bounded and 54000 keeps meaning "ran, result discarded", but the slot spends unbounded time and network on the rest, and the session keeps its enlarged input buffer. A cancel request does not help: `PQcancel` blocks the loop before 17, `PQcancelStart` needs 17 and a second connection, and the rest must be drained anyway.
D. Keep whole-result buffering and document that a result costs its full size per slot before the bound rejects it (8 loops x `--pg-conns` slots).

Sub-question for A to C: keep the SQLSTATE `54000` with a message stating the unknown outcome, or add a distinct, structured "outcome unknown" signal to `Query.Result` (a change of the architectural core `Server.Query`, which every consumer sees)?

Recommendation: A, with 54000 and the outcome stated in its message and docs; B once libpq 17 is the minimum anyway. No option bounds the first oversized row (finding 4); a hard ceiling on received bytes would need a different boundary (the pool speaking the protocol itself, or a process with a resource limit), which is not proposed.

Tests an implementation needs (pg_glue_test.c's fake server, whole, per message and per byte): the mode set on first use and on cached and unnamed executions; zero-row results keep their columns; rows then an error answer the error; overflow mid-result answers 54000 once and closes the session; a result at exactly the bound; a single oversized field; and bench/dbcheck: an INSERT ... RETURNING over the bound.

Decided 2026-11-17 by the coordinating session with sol (consult round 20261117-050608-48d2), under the user's delegation of the same day: option A, single-row collection with session disposal on overflow. Explicit command-boundary state; single-row mode enabled and verified for first-use, cached and unnamed executions; never fall back silently to whole-result buffering; zero-row results keep their columns; partial rows are discarded on a server error; on overflow release the accumulated data, answer once with SQLSTATE 54000 and close through the existing close-after-answer path. Enforce and document the minimum libpq (14.6, 15.1 or 16+, as the item found). Cover the supported versions and the item's fake-server fragmentation cases; measure per-row overhead with this repository's non-production benchmarks. Document that libpq can still buffer one whole protocol message (an oversized row). The sub-question (a structured "outcome unknown" signal in Server.Query) is not decided here: it changes a core contract that ekklesiai.org consumes, so it went to Needs a decision; this item answers with plain 54000.
