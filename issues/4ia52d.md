Count each row and field in Query.maxResultBytes

Seen in tc5rsx: `rows_of` (zig/src/pg.c:176-182) charges a result only its text, the column names' strlen and each value's PQgetlength, against `Query.maxResultBytes` (Server/Query.lean:44-46, "Most bytes of text (field values and column names) a result may hold"). A result of many NULL or empty values passes the 1 MiB bound with almost nothing counted, e.g. `SELECT NULL FROM generate_series(1, 10000000)` counts 0 bytes, yet costs per field a 16-byte PGresAttValue in libpq and an 8-byte array slot in Lean (plus, for a non-NULL value, a 16-byte `Option.some` constructor and a 32-byte string header before its bytes), and per row a Lean array (24 bytes plus 8 per field): hundreds of MB for that query, per pool slot. Invalid UTF-8 replaced by U+FFFD can also make a Lean string longer than the PQgetlength it was charged.

Question: Should the bound charge each row and field a fixed cost (and the converted string size) so that it bounds what a result costs in memory, or stay a bound on text only and document that a result's row and field count is unbounded?
Options: charge a conservative fixed cost per row and per field and the converted size, renaming or redocumenting `Query.maxResultBytes` accordingly | keep the text-only bound and document the unbounded row count
Recommendation: the first, checked before the Lean values are allocated; it goes with the decision on "How a PostgreSQL result over Query.maxResultBytes is received and how it ends the session", which would charge rows as they arrive. A test: a result of many NULL and of many empty values over the new bound answers 54000.

Decided 2026-11-17 by the coordinating session with sol (consult round 20261117-050608-48d2), under the user's delegation of the same day: approved, conservative structural accounting: charge column metadata, every row and field (NULL and empty included) and the converted Lean string storage (UTF-8 replacement expansion included) with object overhead, using overflow-checked arithmetic and charging before allocating. Document Query.maxResultBytes as a conservative budget for the accumulated result, not a process-memory ceiling. Test exact-bound acceptance, overflow, many NULLs, many empty strings and invalid UTF-8. Runs before qsqb5f.
