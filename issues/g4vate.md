Make check.sh fail on a broken relative Markdown link or anchor

Item ejegth moved README.md's sections into docs/ and docs/reports/ with 74 relative links and anchors between them, verified once by a one-off script (every `[text](path#anchor)` outside code in the tracked Markdown files: the path exists, the anchor is a GitHub heading slug of the target). Nothing keeps them valid: renaming a heading or moving a file breaks them silently, and the new rule in AGENTS.project.md ("Where findings go") will add more documents.

Proposal: a small checker (a script under bench/ or a Lean/Go program already in the build) run by check.sh, failing with the file, the link and what did not resolve. Question for the owner: is the cost of one more check in check.sh worth it, or should it stay a manual step at each docs change?

Decided 2026-11-19 by the coordinating session with sol (consult round 20261119-064727-7568, call 0dc8e8af) under the user's delegation to decide the queue with the models: approved. A Go checker (Go is already a build dependency; no Python, no new Lean executable), runnable on its own and run near the start of check.sh. Scope: every git-tracked .md file, issues/ included. Check relative paths, and for Markdown targets and same-file fragments the GitHub heading slug, duplicate-heading suffixes included; other targets only for existence. Parse links properly (inline and reference-style, escaped paths), ignore fenced and inline code, no network checks. Report file, line, link, and whether the path or the anchor failed. Fix links that are broken today rather than excluding files. Note: the stale references wywakf fixed were prose ("README "Memory""), not links, so this check would not have caught them; it guards the 74 links ejegth added and those the "Where findings go" rule will add.
