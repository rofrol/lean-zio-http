Accept that stale-statement recognition relies on PostgreSQL's undocumented source-function field

Found in item i35sos (commit ea3e4fb, zig/src/pg.c): a cached statement is forgotten when the error is 0A000 and its source function (PG_DIAG_SOURCE_FUNCTION) is `RevalidateCachedQuery`. PostgreSQL's documentation names neither that function nor the message text as a contract; it works on PostgreSQL 18, shown by `testSchemaChange` in bench/dbcheck/main.go, and the comment in pg.c says to recheck at each PostgreSQL update. If a later PostgreSQL renames the function, the stale statement is no longer forgotten and every later use of it on that session fails with 0A000 until the session closes (today's pre-i35sos behavior), with no wrong data. Under policy Rule 6 this is a supported-subset contract grounded in the pinned version, which needs the user's approval; only the user accepts the risk.
Question: Keep recognizing stale statements by PostgreSQL's source-function field, rechecked at each PostgreSQL update?
Options: keep it, as a supported-subset contract rechecked at each PostgreSQL update | forget the statement on every 0A000 from an execute of a cached statement (costs a re-prepare on unrelated 0A000s) | close the session instead

Decided 2026-11-17 by the coordinating session with sol (consult round 20261117-090130-75a9); the user asked to check with sol whether newer PostgreSQL has a documented way. No release through 18 documents one. 0A000 is feature_not_supported, with no SQLSTATE of its own for this case. The routine field's value is not documented as stable. PQclosePrepared and PQsendClosePrepared (libpq 17) clean up statements but do not classify errors. Change to option (a), invalidation on a documented superset: on 0A000 or 26000 from executing a cached statement, forget that entry and fail the query without replay. Drop the source-function check. Close the obsolete server-side statement with PQsendClosePrepared, which is safe once 4lmjda makes libpq 17 the minimum, and consume its result, so client and server state stay consistent and no name collides. Do not describe it as recognizing the stale-plan error. Keep i35sos's tests and add one for an unrelated 0A000, which now evicts. Runs after 4lmjda.
