Where an item's time goes: bench.sh's load measurements, not the cold build

The user asked on 2026-11-16 to fix rr2's cold start (every run in this repository starts without a Lake build). Checked the same day with sol (consult round 20261116-174236-8962) against `~/.local/state/rr2/tasks.jsonl`: the cold build costs well under a minute (Lean modules 0.1-1.1 s each, `zig build` about 19 s), while `./bench.sh` took 737-770 s per call and 38-81% of each run's wall time (wwuck5 770 of 951 s, vma67w 737 of 1298 s, 6gmafg 1525 of 3989 s in two calls, lpgru3 757 of 1953 s). Keeping a per-repository Lake snapshot in rr2 would save little and makes one run's build artifacts the next run's starting state (trust and invalidation tests needed); not worth it without a measured gain.
Question: Should an item that does not touch the transport, the parsers or the load generator integrate on bench.sh's correctness checks alone, with the load measurements run only by items that may change performance and on a schedule you set?
Options: keep the full bench.sh as every item's gate (as now) | correctness checks as the gate, measurements only for performance-touching items | split bench.sh into a check script used while editing, keeping the full bench.sh as the gate

Decided 2026-11-17 by the coordinating session with sol (consult round 20261117-011832-74e7), under the user's delegation of the same day to decide the open questions with sol: split bench.sh into a correctness-check script that runs on its own while editing, keeping the full ./bench.sh (load measurements included) as every item's integration gate. No scheduled measurements, no cross-worktree artifact cache.
