Decide whether to ask upstream for request-target count limits apart from maxUriLength

Seen while doing tdtseh: the H1 adapter's retained state is now bounded (README "Memory", "The adapter's state"): at most 653,788 bytes of live blocks per connection while a request is incomplete, 557,224 of them the parsed request-target, so a connection holds at most 715,228 bytes (698.5 KiB), 2.73 GiB at 4,096 connections. `lsrv-test` finds 484,960 bytes for a request line whose target is 8,176 empty query parameters, the most the line allows; `bench/boundary` measured 500.7 to 501.0 KiB of resident growth per connection holding that line (41.6 KiB with the hand-written parser, which keeps no state; M1, 2026-11-17).

The target's element counts cannot be set apart from `maxUriLength` in this repository: `H1.Config` (Std/Http/Protocol/H1/Config.lean) has no field for them, and `requestTargetConfig` (Std/Http/Protocol/H1/Parser.lean:261) sets `maxPathSegments` and `maxQueryParams`, with every other URI limit but the host's, to `maxUriLength`; `parseRequestLineBody` uses it directly. Upstream HEAD is the same (leanprover/lean4 commit 13921a64bf71, 2026-11-16, Parser.lean:268), and its comment states the reason: "`maxUriLength` bounds the whole target, so no component limit lower than it rejects a target the server accepts as a whole, which RFC 9112 §3 would answer with `414`, not `400`." That reads as a deliberate design choice, not a bug, so per AGENTS.md Rule 6 no fork applies; separate limits would be a feature request.

What a count limit would buy: each element costs at most 48 bytes of blocks, plus at most twice its 8-byte slot in the elements array, so a limit of N elements together bounds the target's part by about 64·N bytes plus the elements' bytes, in place of 557,224 (for example N = 1,000 would give about 64 KiB plus the target's bytes, if both counts were limited to N together). No evidence was gathered on what real clients send or on other servers' defaults: that was asked only for the case where the counts could be set here.

Question: Should the per-connection bound stay at what `maxUriLength` = 8,192 gives, or should the target's counts be limited?
Options: accept the derived bound (698.5 KiB per connection, 2.73 GiB at 4,096) | ask upstream (leanprover/lean4) for `maxPathSegments`/`maxQueryParams` in `H1.Config`, with an answer for the 414/400 question (an outward action: needs the user's go) | lower the default connection cap so the total fits a memory budget the owner names

Decided by the user 2026-11-17: ask upstream (leanprover/lean4) for maxPathSegments and maxQueryParams in H1.Config.
