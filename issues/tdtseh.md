Decide how to bound the H1 adapter's state a connection retains

Seen while doing es53kx: no derivation bounds `Conn.State.parser` for H1, and `bench/boundary` measured it far above the withdrawn 98 KiB per connection (README "Memory", M1, 2026-11-17, resident growth per connection while waiting after `100 Continue`): a request-target with 4,000 path segments 208 KiB, with 4,000 query parameters 302 KiB, so 4,096 such connections take about 1.2 GiB. H1 parses the target into an `Array` of segments and a list of parameters and keeps them in the machine's message head until the request completes; `requestTargetConfig` (Std/Http/Protocol/H1/Parser.lean) maps `maxPathSegments` and `maxQueryParams` to `maxUriLength` (8,192 here, `Server.H1Adapter.config`). The other adapter scenarios stayed at 31 to 77 KiB.
Question: How should the per-connection memory of an incomplete request be bounded, if at all?
Options: lower `maxUriLength` for H1 (a 414 for longer targets; still needs an allocation derivation for the rest of the state) | ask upstream for separate `maxPathSegments`/`maxQueryParams` limits in `H1.Config` (an outward action) | keep no parsed head across receives (reparse the head from the buffer once complete) | state a size law for adapters that `Conn`'s memory theorem can use and derive H1's | accept the unbounded state and state the measured figures only
