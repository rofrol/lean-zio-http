Linux pending-connection accept errors end the server process

Moved on 2026-11-16 from ekklesiai.org's queue, where it was item ynroef (moved by its item m4jfmv). Item ids and decisions (D1, D2) named below are ekklesiai.org's; paths are this repository's.
Seen in queue item 55ewev (review round 20261116-065425-266b, sol): Linux accept(2) documents ENETUNREACH, EHOSTUNREACH, EHOSTDOWN, ENONET, ENOPROTOOPT and EOPNOTSUPP as errors of the pending connection ("treat them like EAGAIN by retrying"). The pinned zio (9bef33d, src/os/net.zig `errnoToAcceptError`) maps EOPNOTSUPP to `OperationNotSupported` and the others to `Unexpected`, the same errors a broken listening socket produces (EBADF also maps to `Unexpected`). zig/src/serve.zig `acceptCb` therefore ends the process with `fatal: accept: ...` on them; a supervisor restarts it, dropping every open connection. Whether a remote peer can provoke these (an ICMP error on a pending connection) has not been checked.

Options: (a) ask zio upstream to name these errors (an outward action; under the policy a bug fix would go through a fork with a regression test, but first it must be established from zio's documentation whether this is a bug or an unsupported case); (b) re-arm on `Unexpected` with a bound on consecutive failures, which risks spinning on a broken socket and is a workaround the policy forbids if it is a bug; (c) keep exiting and rely on the supervisor. Documented as unresolved in the README ("Accept errors") and decision record 0001's Consequences.
